# Feature Surface Matrix

## Purpose

Prevent backend capabilities from becoming invisible unfinished work and prevent frontend controls from becoming decorative promises.

Update this matrix whenever an API, command, event, worker, permission, route, or user workflow is added or materially changed.

## Classifications

| Classification | Required evidence |
|---|---|
| `user-facing` | Discoverable authorized UI, real contract/persistence integration, explicit states, responsive/accessibility verification |
| `integration-only` | Versioned contract, machine authorization, idempotency, audit, failure/retry/replay evidence; no UI unless an operator workflow requires it |
| `operations/internal` | Restricted operational path, runbook/observability, audit and recovery evidence; no public UI by default |
| `intentionally deferred` | Owner, reason, target phase, requirement/test reference, and no misleading frontend control |

## Status values

- `planned` — accepted scope but implementation has not started;
- `backend-only gap` — backend exists and a required user surface is missing;
- `frontend-only gap` — frontend exists without a complete backend contract;
- `in progress` — vertical slice is under construction;
- `verified` — required evidence has passed;
- `not applicable` — reviewed and UI or backend counterpart is intentionally unnecessary.

## Combined public-confirmation seam

The public booking and occurrence adapters provide post-commit lifecycle callback seams. Production API composition now maps those seams into tenant-scoped reminder outbox mutations through `packages/database/src/public-communication-hooks.ts`; worker delivery remains outside the booking transaction. `apps/worker/src/public-booking-hooks.ts` and `public-occurrence-hooks.ts` remain reusable event-host adapters and can compose contact verification when an issuer is supplied. The worker process now has a deployable entrypoint and internal probes; live provider secrets and delivery observability remain tracked integration work.

## Pull-request audit

For each changed capability:

1. identify its authoritative backend contract and classification;
2. locate the required frontend route/component, or record why no UI is appropriate;
3. verify authorization and tenant behavior on both sides;
4. exercise loading, empty, validation, failure, degraded, pending, and success states that apply;
5. verify the real API/persistence boundary, not only mocks;
6. record desktop, tablet, mobile, keyboard, focus, zoom, and reduced-motion evidence for user-facing changes;
7. remove or track stale controls and backend-only gaps before declaring completion.
